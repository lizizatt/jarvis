# Copilot Chat Session Integration Feasibility

## Decision

Build a supported, opt-in integration for conversations addressed to a new
`@jarvis` VS Code Chat Participant. Do not attempt to enumerate, import, edit,
or create arbitrary GitHub Copilot Chat sessions.

This delivers a useful shared history for new Jarvis conversations: a user can
find the conversation in the Copilot Chat session list on the VS Code host and
in Jarvis's per-repository history. It does not make all existing Copilot
conversations visible in Jarvis, and it cannot turn a conversation that started
in the Jarvis PWA into a native Copilot Chat session.

## Evidence

Jarvis currently persists its own `tasks` and `task_events` in SQLite. Its
worker selects a `LanguageModelChat` and calls `sendRequest`; its `sessionId` is
a Jarvis/CLI correlation ID, not a VS Code Copilot Chat session ID. The web
client's `nativeSessionId` is only a compatibility alias for that field.

The supported VS Code API exposes `vscode.chat.createChatParticipant`. A
participant receives the request and `ChatContext.history` for the *current*
session, restricted to messages addressed to that participant. It exposes no
API to list sessions, obtain their IDs, open an existing session, create a
session, or observe conversations handled by Copilot or another participant.

Sources:

- [VS Code Chat Participant API](https://code.visualstudio.com/api/extension-guides/chat)
- [VS Code API reference: chat](https://code.visualstudio.com/api/references/vscode-api#chat)
- [VS Code Language Model API](https://code.visualstudio.com/api/extension-guides/language-model)

VS Code persists chat state locally, but it is internal Copilot/VS Code state,
not an extension contract. Repository policy also prohibits inspecting private
Copilot chat or extension storage. Depending on it would be version-fragile,
unsafe around concurrent writes, and unacceptable for this product.

## Recommended Architecture

1. Register one `@jarvis` Chat Participant in `apps/vscode-worker`.
2. On every `@jarvis` request, create or continue a Jarvis task through the
   existing server WebSocket protocol. Store a new `origin` value of
   `vscode-chat` and a stable opaque `clientConversationId` generated by the
   extension; do not label it as a native Copilot session ID.
3. Stream task progress and the final answer into the participant response.
   Mirror the user request, response, timestamps, model, and task ID to
   Jarvis's SQLite history.
4. In the Jarvis UI, group these tasks under the repository's conversation
   list, mark them `VS Code Chat`, and provide the task detail URL. The user
   opens the matching native chat from VS Code's ordinary Chat history; Jarvis
   cannot deep-link to a precise native session with a supported API.
5. Preserve the existing PWA-to-worker flow as a distinct `jarvis-pwa` origin.
   It remains visible in Jarvis only.

The server must remain the task-system source of truth. The participant should
not duplicate task execution, task state transitions, cancellation, or event
storage in the extension.

## Feasibility And Risks

| Requirement | Result | Reason |
| --- | --- | --- |
| Show all existing Copilot sessions per repository in Jarvis | Not feasible safely | No public enumeration/read API; private state is prohibited and unsupported. |
| Track new `@jarvis` VS Code Chat conversations in Jarvis | Feasible | The participant receives its own prompts and history and can mirror them. |
| Find a new Jarvis conversation in the host Copilot session list | Feasible | VS Code owns persistence for the session containing the participant exchange. |
| Start in Jarvis PWA and create/find that same native Copilot session | Not feasible | No supported session-create, session-ID, or targeted-open API. |
| Continue a pre-existing Copilot conversation from Jarvis | Not feasible | Jarvis cannot receive or address that conversation's session handle. |

The main product trade-off is explicit invocation: the conversation is recorded
in both places only when the user starts or continues it with `@jarvis` in VS
Code. Participant history is scoped to `@jarvis`, so it must not be presented as
a complete transcript of the entire Copilot chat.

## Prototype Gate

Before product implementation, add a small worker-only spike and validate it
manually in a disposable repository:

1. Register `@jarvis` and stream a fixed response.
2. Send two requests in one Chat session and verify that participant-scoped
   `ChatContext.history` contains the first exchange.
3. Forward both requests to a fixture Jarvis server and verify the resulting
   task/event ordering, cancellation, and reconnection behavior.
4. Restart VS Code and verify the Chat UI preserves the conversation while
   Jarvis history remains independently accessible.

Exit the spike if a supported API surface does not deliver participant request
handling and scoped history in the target VS Code release. Do not widen it into
a private-storage reader as a fallback.

## Estimated Work

The spike is small (one extension contribution, handler, and fixture tests).
The supported production feature is medium-sized: protocol/task-origin schema
migration, participant-to-server request lifecycle, event-to-chat rendering,
UI provenance, reconnection/cancellation tests, and VS Code-hosted integration
tests. The unsupported requirements require a new upstream VS Code/Copilot API,
not more Jarvis implementation effort.
